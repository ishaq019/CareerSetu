# CareerSetu LLM Workflow

## Design principle

Do not send every request to an LLM. CareerSetu uses deterministic code for facts that can be calculated cheaply and uses the LLM where language understanding or generation adds real value.

## 1. Job-fit analysis

```text
Resume + JD
  -> normalize text
  -> deterministic skill/requirement extraction
  -> evidence matching
  -> Match Score + ATS-oriented coverage
  -> skill gaps + baseline roadmap
```

The score is not generated by an LLM. This keeps it repeatable and auditable.

Optional authenticated AI explanations can be added after the deterministic report. The LLM must explain evidence rather than change the underlying score.

## 2. CareerSetu RAG chat

Career chat is a **2-step RAG** workflow because retrieval is a clear prerequisite for a knowledge-grounded answer and this keeps latency/cost predictable.

```text
User question
  -> embedding
  -> Chroma top candidates
  -> lexical + vector hybrid rerank
  -> deduplicate
  -> context budget
  -> structured LLM output
  -> citation validation
  -> answer + sources
```

The model is explicitly instructed that retrieved documents are untrusted data, not instructions. The answer schema contains `answer`, `confidence`, and citation numbers. The API validates citation indexes before returning them.

## 3. Why hybrid retrieval

Pure vector search can miss exact technical terms such as `useMemo`, `O(log n)`, `JWT`, or `MongoDB`. CareerSetu retrieves a larger candidate set and blends vector similarity with lightweight lexical overlap before the final top-k context is built.

This is intentionally cheaper than calling an LLM as a reranker for every request. A learned reranker can be added after retrieval evaluation proves it is needed.

## 4. Document ingestion

```text
PDF/DOCX
  -> page-aware extraction
  -> normalize
  -> recursive structure-aware chunking
  -> topic metadata
  -> deterministic chunk IDs
  -> embedding model
  -> Chroma upsert
```

Stable IDs make re-ingestion idempotent. Page metadata enables source-level evidence in answers.

## 5. Interview workflow

LangGraph is used where state and adaptive control are actually useful:

```text
Candidate profile
      |
      v
Retrieve relevant interview material
      |
      v
Ask question
      |
      v
Candidate answer
      |
      v
Structured LLM evaluation
      |
      +--> score / strengths / improvements
      |
      v
Adjust difficulty
      |
      v
Next question
```

The graph is intentionally small at first. More nodes should be added only when each node has a meaningful failure/retry/state boundary.

For production, persist LangGraph checkpoints in PostgreSQL so an interrupted interview can resume. LangGraph's PostgreSQL checkpointer is the intended production integration.

## 6. LLM controls

- Separate fast and quality models by task.
- Temperature 0 for scoring/evaluation/grounded answers.
- Explicit request timeout.
- Bounded retries.
- Bounded output tokens.
- Bounded context characters.
- Pydantic structured output instead of fragile JSON parsing.
- Never allow the LLM to invent resume experience or skills.
- Never treat retrieved text as system instructions.
- Validate citations returned by the model.

## 7. Cost control

A normal guest job-fit analysis requires **zero LLM calls** in the baseline path.

A grounded chat request uses:

- one embedding call
- one LLM generation call

Interview evaluation uses one structured LLM call per submitted answer. The question-selection step should prefer an already retrieved knowledge-base question before asking the LLM to generate a new one.

## 8. Failure strategy

If the LLM is unavailable:

- Guest job-fit analysis still works.
- Document parsing still works.
- Auth still works.
- Chat returns a controlled 503 rather than hallucinating.
- Interview evaluation returns a controlled 503.

The system must never fabricate a grounded answer just because the model is unavailable.
